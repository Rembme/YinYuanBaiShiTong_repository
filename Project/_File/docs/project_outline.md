## 一、项目目标与范围确认

### 1. 要解决的问题

- 用户目前只能逐页浏览，不能按自然语言表达的问题查找相关通知和制度。
- 不同用户看到的内容相同，缺少按个人需求订阅的能力。
- 用户需要通过对话快速了解校园通知，并能连续追问。
- 用户希望自动收到与自己订阅专区相关的周报。

### 2. 用户角色

#### 学生用户

- 搜索、查看通知、政策及来源。
- 与智能助手进行多轮对话。
- 创建、切换和删除自己的会话。
- 订阅或取消订阅通知专区。
- 查看自己的周报并接收邮件推送。

#### 管理员

- 管理采集来源、专区分类和同步任务。
- 查看数据更新情况、失败任务和重复内容。
- 管理用户或处理需要人工审核的内容。
- 查看运行状态，但不能在界面或日志中泄露用户凭据。

### 3. 确认四个通知专区

要求文档提出“四大通知专区”，并列出三类主要网站来源及其他学校网页。以下作为待确认的初步映射，正式开发前应固定专区名称和来源归属：

1. 信息工程学院：`https://mie.bigc.edu.cn/`
2. 北京印刷学院官网：`https://www.bigc.edu.cn/index.htm`
3. 北京印刷学院新闻网：`https://news.bigc.edu.cn/`
4. 其他经确认的北京印刷学院官方网页。

每个专区需要明确：

- 展示名称和说明。
- 对应网站、栏目和页面路径。
- 哪些内容属于通知，哪些仅作为新闻或背景资料。
- 订阅后推送哪些内容。
- 更新频率和页面失效处理规则。

### 4. 第一版功能范围

第一版应打通以下流程：

- 官方网页采集。
- 知识库 PDF 入库。
- 自然语言检索和带来源回答。
- 多轮对话与会话管理。
- 用户专区订阅。
- 智能周报生成和推送。
- SSE 流式输出。
- 学生与管理员权限控制。

视频解析、视频问答和视频内容入库不纳入本阶段。

**本阶段交付物：**产品需求说明、角色与权限表、四专区定义表、功能优先级清单、待确认事项清单。

## 三、知识库 PDF 处理方案

### 1. 建立目录和版本索引

PDF 目录涉及以下主题：

- 教学与管理工作规范。
- 师资管理与奖励。
- 教学质量管理。
- 教学改革与建设。
- 教务管理。
- 学务管理，包括学籍、考试、转专业等。
- 实践教学管理。
- 教材管理。

对每项制度记录名称、所在页码、发布时间或修订时间、适用对象和适用期限。

### 2. 提取内容并保留出处

- 提取 PDF 文本，检查中文乱码、缺页和页面顺序。
- 识别目录、章节、条款和页码，优先按制度及条款边界切分。
- 只对扫描页或文本提取失败的页面安排 OCR。
- 给每个知识片段附上文档名称、章节、条款、PDF 页码和版本信息。
- 检索回答应能指向 PDF 页码和具体条文，不能只返回无出处摘要。

### 3. 标记时效性与版本冲突

- 根据发布日期、修订状态和有效期限标记内容。
- 对有明确年份的计划或方案标注年份范围。
- 新旧版本冲突时分别保留版本信息，不将不同版本混合回答。
- 涉及现行有效性的问题，优先核对学校官方来源；无法确认时说明材料日期和不确定性。
- 建立重新导入 PDF 和更新索引的流程。

**阶段验收：**针对学籍、考试、教学管理和实践教学等代表性问题，系统能找到正确制度，并返回制度名称、页码及相关条文。

## 四、系统架构与技术决策

要求文档推荐以下技术栈。正式编码前应写入架构说明，并核对各组件版本兼容性，特别是 Spring Boot 3.4 与 Java 25 的组合。

- 后端：Spring Boot 3.4、Java 25。
- AI 框架：Spring AI Alibaba。
- 大模型：DeepSeek V4pro。
- 向量模型：text-embedding-v2，1536 维。
- 数据库：PostgreSQL 16。

- 认证授权：Spring Security、JWT。

- 网页采集：Jsoup、Readability4J。

架构设计需要明确：

- 浏览器、前端、后端及 SSE 的请求路径。
- 网页采集、文本清洗、知识切分、Embedding 和向量入库的数据链路。
- PostgreSQL 业务数据与 PGVector 向量数据的关系。
- 实时通知查询与静态制度检索的分流规则。
- 周报定时任务、邮件投递和失败重试方式。
- 模型、爬虫和邮件服务的超时、错误及降级策略。
- 开发、测试、生产配置的隔离方式。
- 组件版本、运行环境和部署方式。

## 五、数据采集与内容管理

### 1. 采集来源管理

- 配置三类主要来源及经确认的其他学校官方网页。
- 维护来源名称、所属专区、首页 URL、栏目 URL 和允许采集的域名。
- 将采集范围限定在明确的页面和栏目内。
- 设置合理的并发量、访问间隔、超时和重试次数。
- 记录每次任务的运行时间、处理结果和错误原因。

### 2. 页面解析与字段抽取

每条通知尽量保存：

- 标题、正文、发布单位。
- 发布时间、更新时间和采集时间。
- 原始 URL、所属专区和栏目。
- 附件名称及附件链接。
- 内容哈希或版本标识。

### 3. 去重、更新和撤下

- 通过规范化 URL、标题和正文哈希识别重复内容。
- 页面更新后保存新版本或更新时间，避免静默覆盖。
- 页面失效、撤下或 URL 变更时记录状态。
- 周报和检索结果展示发布时间及采集时间。
- 为解析失败的页面保留错误记录，方便管理员排查。

### 4. 采集任务管理

- 支持首次全量采集和定期增量采集。
- 支持管理员手动触发指定专区的采集。
- 任务应具有状态、重试、失败原因和处理数量记录。
- 防止重复启动任务导致数据重复或模型重复调用。

## 六、数据库与核心数据模型

编码前至少设计以下实体及其关联：

- 用户：身份、角色、状态、创建时间。
- 通知来源：网站、栏目、专区、采集规则。
- 通知记录：标题、正文、发布日期、原文链接、状态和版本。
- 知识文档：文件名称、版本、导入时间、有效期或修订信息。
- 知识片段：正文、页码、章节、Embedding、文档关联。

- 消息：会话、角色、正文、引用来源和时间戳。

- 周报：用户、周期、内容、引用通知和发送状态。

同时定义数据库迁移、索引、软删除策略、备份和恢复方式。

## 七、智能检索与对话功能

### 1. 按时效性分流查询

- “本周有什么通知”“最新报名截止日期”等问题优先查询实时通知。
- “请假规定是什么”“转专业条件是什么”等问题优先检索知识库 PDF。
- 同时涉及制度与新通知的问题组合两类来源，并分开标注出处。
- 找不到可靠依据时明确说明未检索到，不编造规定。

### 2. RAG 回答链路

- 对问题做意图识别和查询改写。
- 按关键词、语义向量、专区、时间和来源检索。
- 对结果排序、去重，并排除明显过期或无关内容。
- 将相关片段和出处交给模型生成回答。
- 回答提供通知链接、制度名称、PDF 页码或原文条款。
- 对冲突来源标明版本或发布日期。

### 3. 多轮会话

- 支持创建、切换和删除会话。
- 按要求保留约 20 轮连续对话上下文。
- 会话及消息按用户隔离。
- 对长会话采用摘要或截断策略，控制上下文长度。
- 支持连续追问和切换新主题。
- 按预先定义的策略处理已删除会话及关联消息。

### 4. 回答质量和出处

- 事实性回答尽可能附上引用。
- 引用能够打开原始网页或定位 PDF 页码。
- 区分通知、新闻与制度材料。
- 对有效期、报名状态等无法判断的情况提示用户核对原文。
- 日志只保留排查所需的信息，不记录密钥。

## 八、用户认证与安全权限

- 确定登录来源，不默认虚构学校统一身份认证能力。
- 设计 JWT 颁发、过期、刷新和退出策略。
- 至少区分 `STUDENT` 与 `ADMIN` 两种角色。
- 学生仅能访问自己的会话、消息、订阅和周报。
- 管理员接口逐项授权，不能只依赖前端隐藏按钮。
- 对登录、模型调用、订阅变更及管理接口进行输入校验和必要限流。
- 对日志、异常信息和前端错误提示做脱敏。
- 明确个人数据的保留期限、删除规则和备份范围。

## 九、个性化订阅管理

- 用户可以浏览四个专区的名称、简介和近期更新。
- 用户可以逐个订阅或取消订阅。
- 支持自然语言提出订阅需求，例如“订阅信息工程学院通知”。
- 自然语言识别不确定时，先让用户确认专区再保存。
- 订阅数据与用户账户关联并持久化。
- 周报只纳入用户已订阅专区的有效内容。
- 订阅变化后更新相关缓存，避免继续推送旧专区组合。
- 无新内容时采用清楚的空状态，避免生成误导性周报。

## 十、智能周报与推送

- 确定周报周期、时区、发送时间和补发规则。
- 按用户订阅组合收集周期内的新通知。
- 生成按专区组织的周报，包含标题、摘要、发布时间和原文链接。
- 对截止日期、报名时间等关键信息保留原文来源。
- 支持在对话界面查看周报并通过邮件推送。
- 邮件失败时记录状态并按规则重试。
- 通过订阅组合键缓存降低重复模型调用，并处理通知更新后的缓存失效。
- 支持用户停止邮件推送或修改偏好。
- 邮件服务尚未在要求文档中指定，实施前需确定服务和发件人配置。

## 十一、SSE 流式响应

- 定义开始、内容增量、引用来源、完成和错误等事件格式。
- 模型生成时逐步向前端返回内容。
- 为较慢的模型调用和采集任务配置异步处理或专用线程池。
- 处理超时、客户端断开、主动取消和错误恢复。
- 连接断开后释放相关资源。
- 校验用户是否有权读取当前会话。
- 检查代理或服务器缓冲行为，确保前端可以实时接收内容。
- 确保最终回答、引用和流式内容保持一致。

## API key 文件的查看时机

建议在 AI 服务适配器和本地配置方式已经确定之后、第一次真实调用 DeepSeek V4pro 之前，再检查 `DeepSeek_API_key.txt` 是否可供本地配置读取。需求整理、架构设计、数据库、网页采集、知识库入库和模拟模型流程均不需要先读取密钥。

1. 完成需求问题清单、四专区定义和版本兼容性核对。
2. 完成架构图、数据库设计和接口约定。
3. 建立应用骨架、认证和数据库迁移。
4. 开发网站采集与通知存储。
5. 导入知识库 PDF，建立带页码的检索索引。
6. 完成 RAG、查询分流、多轮对话和 SSE。
7. 完成专区订阅、周报生成及邮件推送。
8. 补齐管理页面、安全、部署和运维文档。
9. 按验收计划逐项验证；如需补充体验设计，再根据用户指示查看答辩 PPT 或展示视频。
